# TokenBank 智能合约架构

## 1. 目标

说明 TokenBank 链上合约的职责划分、核心交互时序、安全机制及潜在风险。

## 2. 关键结论

- 共 3 个合约：`MyToken`（支持 EIP-2612 的 ERC20 代币）、`TokenBankPermit2`（支持 Permit2 存款的银行合约）和 **Uniswap Permit2**（签名授权转账，独立部署）。
- `MyToken` 继承 OpenZeppelin 的 `ERC20Permit`，实现 EIP-2612 签名授权，支持离线 approve。
- `TokenBankPermit2` 在构造时绑定底层代币地址和 Permit2 地址，提供传统 `deposit` 和 `depositWithPermit2` 两种存款方式。Permit2 地址通过环境变量注入，需提前部署。
- 取款遵循 Checks-Effects-Interactions 模式，配合 `ReentrancyGuard` 防范重入。
- `depositWithPermit2` 使用 Uniswap Permit2 的 `permitTransferFrom`，用户签名一次即可完成转账，无需提前发起 approve 交易。

## 3. 合约清单

| 合约 | 文件 | 核心职责 | 关键依赖 |
|------|------|----------|----------|
| MyToken | `contracts/src/MyToken.sol` | ERC20 代币，支持铸造、销毁、EIP-2612 Permit | OpenZeppelin ERC20 / ERC20Permit / Burnable / Ownable |
| TokenBankPermit2 | `contracts/src/TokenBankPermit2.sol` | 接收、记录并返还用户存入的代币，支持 Permit2 存款 | OpenZeppelin IERC20 / SafeERC20 / ReentrancyGuard，IPermit2 |
| Permit2 | `contracts/lib/permit2/` | Uniswap Permit2 合约，提供签名授权转账能力 | 外部依赖，通过 `DeployPermit2.s.sol` 独立部署 |
| IPermit2 | `contracts/src/IPermit2.sol` | Permit2 接口定义，供 TokenBankPermit2 调用 | 无 |

## 4. 状态与函数

### 4.1 MyToken

- 构造时向部署者铸造全部初始供应量（`initialSupply * 10^18`）。
- `decimals()` 固定返回 18。
- `mint(to, amount)` 仅 owner 可调用。
- 继承 ERC20Permit，自动提供 `permit()`、`nonces()`、`DOMAIN_SEPARATOR()` 方法。

### 4.2 TokenBankPermit2

| 类型 | 名称 | 说明 |
|------|------|------|
| 状态 | `token` | 不可变的底层 ERC20 地址 |
| 状态 | `permit2` | 不可变的 Permit2 合约地址 |
| 状态 | `balances[address]` | 用户在 Bank 中的存款余额 |
| 写函数 | `deposit(uint256 amount)` | 传统存款：从用户转入代币并增加存款余额（需提前 approve） |
| 写函数 | `depositWithPermit2(PermitTransferFrom permitTransfer, address owner, bytes signature)` | Permit2 存款：使用 Permit2 签名完成转账，单笔交易完成 |
| 写函数 | `withdraw(uint256 amount)` | 校验余额后返还代币 |
| 读函数 | `balanceOf(address)` | 查询用户存款余额 |
| 事件 | `Deposit(address user, uint256 amount)` | 传统存款事件 |
| 事件 | `Permit2Deposit(address user, uint256 amount)` | Permit2 存款事件 |
| 事件 | `Withdraw(address user, uint256 amount)` | 取款事件 |
| 错误 | `ZeroAmount` | 金额为 0 |
| 错误 | `ZeroAddress` | 代币或 Permit2 地址为 0 |
| 错误 | `InsufficientBalance` | 余额不足 |

## 5. 调用时序

### 5.1 传统存款时序（Approve + Deposit）

```
用户
  │ 1. approve(TokenBankPermit, amount)
  ▼
MyToken
  │ 授权 TokenBankPermit 可动用用户代币
  ▼
用户
  │ 2. deposit(amount)
  ▼
TokenBankPermit
  │ 调用 token.safeTransferFrom(user, TokenBankPermit, amount)
  │ balances[user] += amount
  │ emit Deposit(user, amount)
```

### 5.2 Permit2 存款时序（一键签名存款）

```
用户（链下）
  │ 1. 签名 EIP-712 typed data（PermitTransferFrom 结构体）
  │    domain = { name: "Permit2", chainId, verifyingContract: PERMIT2_ADDRESS }
  │    message = { permitted: { token, amount }, spender: TokenBankPermit2, nonce, deadline }
  ▼
用户（链上）
  │ 2. depositWithPermit2(permitTransfer, owner, signature)
  ▼
TokenBankPermit2
  │ 调用 permit2.permitTransferFrom(permitTransfer, transferDetails, owner, signature)
  │   → Permit2 验证签名，调用 token.safeTransferFrom(owner, TokenBankPermit2, amount)
  │ balances[owner] += amount
  │ emit Permit2Deposit(owner, amount)
```

### 5.3 取款时序

```
用户
  │ withdraw(amount)
  ▼
TokenBankPermit
  │ require(amount > 0)
  │ require(balances[user] >= amount)
  │ balances[user] -= amount          // 先改状态
  │ token.safeTransfer(user, amount)  // 再转账
  │ emit Withdraw(user, amount)
```

## 6. 安全机制

| 机制 | 实现位置 | 作用 |
|------|----------|------|
| 零地址检查 | `TokenBankPermit2.constructor` | 防止绑定无效代币或 Permit2 地址 |
| 金额检查 | `TokenBankPermit2.deposit/depositWithPermit2/withdraw` | 拒绝 0 金额或超额取款 |
| 重入防护 | `TokenBankPermit2` 继承 `ReentrancyGuard` | 防止存款/取款/depositWithPermit2 重入攻击 |
| CEI 模式 | `TokenBankPermit2.withdraw` | 先更新状态再转账，降低重入风险 |
| 安全转账 | `SafeERC20.safeTransferFrom` / `safeTransfer` | 兼容非标准 ERC20 并实现调用失败回滚 |
| Permit2 验证 | `Permit2.permitTransferFrom`（Uniswap） | EIP-712 签名验证，含 nonce 防重放、deadline 防过期 |
| Token 校验 | `TokenBankPermit2.depositWithPermit2` | 确保签名的 token 与合约绑定的 token 一致 |

## 7. Uniswap Permit2 详解

### 7.1 核心概念

Uniswap Permit2 是一个独立的合约，允许用户通过**链下签名**完成代币转账，无需提前发起 approve 交易：

- **签名结构**：用户对 EIP-712 typed data 签名，包含 `permitted: { token, amount }`、`spender`、`nonce`、`deadline`。
- **nonce 机制**：使用 bitmap 机制管理 nonce，支持无序使用，防止签名重放。
- **deadline**：签名有效期，过期后 permitTransferFrom 调用失败。
- **spender**：签名中必须指定 spender（即 TokenBankPermit2 合约地址）。

### 7.2 与传统方式的对比

| 对比项 | 传统 Approve + Deposit | Permit2 Deposit |
|--------|----------------------|----------------|
| 交易数 | 2 笔（approve + deposit） | 1 笔（depositWithPermit2） |
| 用户操作 | 签名 2 次 | 签名 1 次（链下 EIP-712） |
| Gas 费用 | 更高（两笔交易） | 更低（一笔交易，签名 + transferFrom） |
| 前置条件 | 需要先发起 approve 交易 | 需先 approve Permit2 合约（一次性） |

### 7.3 Permit2 EIP-712 签名结构

```typescript
const domain = {
  name: 'Permit2',
  chainId,
  verifyingContract: PERMIT2_ADDRESS,
};

const types = {
  PermitTransferFrom: [
    { name: 'permitted', type: 'TokenPermissions' },
    { name: 'spender', type: 'address' },
    { name: 'nonce', type: 'uint256' },
    { name: 'deadline', type: 'uint256' },
  ],
  TokenPermissions: [
    { name: 'token', type: 'address' },
    { name: 'amount', type: 'uint256' },
  ],
};

const message = {
  permitted: { token: TOKEN_ADDRESS, amount },
  spender: TOKENBANK_ADDRESS,
  nonce,
  deadline,
};
```

**注意**：Permit2 的 domain 不包含 `version` 字段，这是与 EIP-2612 的重要区别。

## 8. 风险与注意事项

- **代币风险**：TokenBankPermit2 假设底层代币符合 ERC20 标准，不包含 rebase 代币、转账税代币等特殊逻辑处理。
- **权限风险**：当前 TokenBankPermit2 无 owner、无 pause、无紧急提现，部署后不可变更。
- **Permit2 签名风险**：用户签名后，任何人在 deadline 前都可提交该签名；前端应确保签名仅发送到目标合约。
- **Permit2 依赖风险**：TokenBankPermit2 依赖 Uniswap Permit2 合约，需通过 `DeployPermit2.s.sol` 提前部署并通过 `PERMIT2_ADDRESS` 环境变量注入地址。
- **小数精度**：合约层面使用原始 uint256；前端需按 `decimals = 18` 进行格式化与解析。
