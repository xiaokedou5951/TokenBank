# TokenBank EIP-7702 改造设计：MetaMask 官方 Delegator + 单笔交易完成授权与存款

## 一、目标与方案摘要

**目标**：用户将 EOA 通过 EIP-7702 授权（委托）给 MetaMask 官方 Delegator 合约 `0x63c0c19a282a1B52b07dD5a65b58948A07DAE32B`（EIP7702StatelessDeleGator），并在**一笔交易**内同时完成「7702 委托 + ERC20 授权 + 存款」。

**核心方案**：利用 EIP-7702 Type-0x04 交易 + MetaMask Delegator 的 ERC-7579 批量执行接口：

```
Type-0x04 交易:
  from              = 用户 EOA
  to                = 用户 EOA（自调用）
  authorizationList = [EOA 签名的授权 → 委托至 0x63c0...32B]
  data              = execute(BatchDefault, abi.encode(Execution[]))

Execution[0] = { target: TOKEN,     callData: approve(tokenBank, amount) }
Execution[1] = { target: TOKENBANK, callData: deposit(amount) }
```

执行顺序：协议先处理 `authorization_list`（EOA code 变为 `0xef0100 || 0x63c0...32B`）→ 再执行交易 data → Delegator（`onlySelf` 校验通过，因 to == from == EOA）依次原子执行 approve 和 deposit → `deposit()` 中 `transferFrom(msg.sender=EOA, ...)` 因前一步 approve 而成功。

**一条交易、一次签名，完成全部三步操作。**

**关键技术调研结论**：
1. MetaMask Delegator（`EIP7702StatelessDeleGatorImpl`）批量执行接口（已从 `@metamask/delegation-abis` v2.0.0 确认 ABI）：
   ```solidity
   function execute(bytes32 _mode, bytes _executionCalldata) external payable;
   // Execution = struct { address target; uint256 value; bytes callData; }
   // BatchDefault mode = 0x0100...0000（64 位 hex）
   // _executionCalldata = abi.encode(Execution[])
   // 权限：仅 address(this)（EOA 自身）或 EntryPoint 可调用
   ```
2. **MetaMask 不向 DApp 暴露 `signAuthorization`**（7702 授权签名仅在钱包内部实现，且有 Delegator 白名单）。DApp 侧唯一正确路径是 **ERC-5792 `wallet_sendCalls`**（wagmi `useSendCalls`）：用户开启 MetaMask 智能账户后，钱包自动完成 7702 授权签名（委托至官方 0x63c0...）并把多个 calls 原子打包成一笔 Type-4 交易。
3. viem 直签路径（`signAuthorization` + `sendTransaction({ authorizationList })`）适用于本地私钥账户（Anvil 账户/嵌入式钱包），用于确定性自动化验证，**不适用浏览器 MetaMask**。
4. `0x63c0...32B` 只部署在主网/Sepolia 等真实链；本地 Anvil 31337 上不存在，需 fork Sepolia 或注入真实字节码。
5. 授权 nonce 规则：当交易发送者 == 授权者（EOA 自付 gas 自调用）时，`authorization.nonce = 账户当前 nonce + 1`（viem `executor: 'self'` / MetaMask 内部均会正确处理）。

## 三、架构设计

### 3.1 双路径设计（按钱包能力自动选择）

```
用户点击「7702 一键存款」
        │
        ├─ 路径 A（浏览器 MetaMask，主 UX）:
        │    wallet_sendCalls([approve, deposit])          ← wagmi useSendCalls
        │    MetaMask 检测智能账户（未开启则引导/被动升级提示）
        │    → 钱包内部签署 7702 授权（→0x63c0...32B，白名单）
        │    → 发送一笔 Type-4 交易: delegation + executeBatch([approve, deposit])
        │
        └─ 路径 B（本地 Anvil / 自动化验证，绕过 MetaMask）:
             viem signAuthorization({ executor: 'self' })   ← 本地私钥账户
             sendTransaction({ to: EOA, data: executeBatch calldata, authorizationList: [auth] })
```

两条路径最终在链上产生**完全相同**的一笔 Type-4 交易，委托目标均为 MetaMask 官方 Delegator。

### 3.2 合约层零改动（重要架构决策）

`TokenBankPermit` 与 `MyTokenPermit` **逻辑零修改**：
- EIP-7702 委托发生在**交易协议层**（authorization_list 由 EVM 处理），智能合约无法也无需感知；
- 委托后 `deposit()` 收到的 `msg.sender` 仍是 EOA 地址，`transferFrom`/`allowance`/事件全部照常工作；
- 批量中的 approve 由 Delegator 以 EOA 身份调用，与用户手动 approve 等价。

改造集中在：**对真实 Delegator 字节码的回归测试、前端交互层、E2E 环境**。

## 五、关键设计决策与理由

| # | 决策 | 理由 |
|---|---|---|
| 1 | 合约零逻辑改动 | 7702 委托在交易协议层完成，`deposit()` 语义完全兼容；改合约属过度设计 |
| 2 | MetaMask 走 `wallet_sendCalls` 而非自组 Type-4 交易 | MetaMask 不暴露 `signAuthorization` 给 DApp（安全设计+白名单）；sendCalls 是官方唯一路径，且由钱包处理授权签名与 nonce |
| 3 | 测试用 `vm.etch` 注入真实 Delegator 字节码 + `vm.etch(user, 0xef0100‖addr)` 模拟委托 | 与主网行为字节码级一致（非 mock）；hermetic 离线可跑、不依赖 fork RPC；Foundry 1.5.1 完整支持 |
| 4 | approve 默认精确金额、参数化 | 即用即销最安全，额度语义与现有 UI 一致；参数化保留灵活性（用户对授权策略未指定具体方案，取安全默认+可扩展） |
| 5 | 三种存款方式并存 | 教学项目定位，展示 UX 演进；不破坏既有功能与测试 |
| 6 | e2e 脚本放在 frontend/scripts 并复用其 viem 依赖 | 无需新增依赖与工作区配置 |
